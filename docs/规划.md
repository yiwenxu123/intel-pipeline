# Intel Pipeline 产品现状分析与迭代规划

基于对代码库（约 6,300 行核心代码、44 个测试）、`docs/PRODUCT_PLAN.md` 执行对照、以及 Dashboard/API 的实地审查，以下是一份面向**真实商业产品迭代**的分析与规划。

---

## 一、产品定位（当前应是什么）

Intel Pipeline 不是通用新闻聚合器，而是**垂直行业情报运营系统**：

| 维度 | 定位 |
|------|------|
| 用户 | 行业分析师、内容运营、投资研究（内部使用） |
| 价值 | 把 50+ 信源的噪音压缩成**每日可决策的精选情报** |
| 差异化 | 领域可插拔 + LLM 语义筛选 + 自动进化（信源/关键词/评分校准） |
| 交付形态 | Dashboard 日报 + 飞书推送 + RSS + Agent Skill |

**商业成功标准**不是「功能多」，而是：

1. 用户**每天 10 分钟内**完成情报消费
2. 精选内容**可直接用于写作/决策**，无需二次大量筛选
3. 运维成本可控（LLM 费用、信源失效可感知）
4. 新领域上线成本 < 1 周（配置驱动）

## 三、代码架构现状

### 3.1 引擎层（`engine/`）— 架构健康

```
CLI (click) → pipeline.py (编排) → fetcher / filter / output / evolution
                    ↓
              store.py (SQLite) + domain.py (配置加载)
```

**优点**：
- 领域无关设计清晰，`domains/` 六文件契约成立
- `run_full_pipeline()` 被 CLI 与 Scheduler 共用，避免重复
- 进化模块已嵌入 pipe 后处理（lifecycle → keyword staging → scoring calibration）

**技术债**：
- `filter` 命令仍手动 `store.close()`，未全面 `with Store()`
- Token 用量仅在内存中（`llm_client.get_usage()`），重启即丢失
- `get_stats()` 仅返回 `total_fetched / selected`，缺 `last_fetch_time`、`by_category`
- 无 fetcher / evolution 单测，重构风险偏高

### 3.2 数据流（已验证）

```
sources.yaml → fetch_all (全量) → raw_items
  → score_items (7天窗口, max 50条/pipe) → scored_items
  → report (昨日精选) → Markdown/JSON
  → notify_report (飞书) → Dashboard API
  → evolution (自动降级/关键词验证/评分校准)
```

**设计取舍合理**：采集全量、LLM 控窗口、API 按分类 `freshness_days` 过滤。

### 3.3 进化模块 — 从「死代码」到「活功能」

| 能力 | 实现 | 运营化程度 |
|------|------|------------|
| 信源生命周期 | `source_lifecycle.py` + Dashboard 禁用/启用 | 中（需定期看健康 Tab） |
| 关键词扩展 | `keyword_staging` 自动验证 + `--apply` | 低（流程未文档化） |
| 评分校准 | `scoring_injector` 注入下次 prompt | 中（黑盒，用户难感知） |
| 进化 API | `/api/health`、`/api/evolution` | 中（健康 Tab 显示 source_id 而非名称） |

## 四、界面与体验现状

### 4.1 Dashboard（`engine/output/templates/dashboard.html`，863 行）

**已实现**：
- 四 Tab：日报 / 政策追踪 / 深度阅读 / 系统健康
- 日/周/月范围、日期导航、分类/信源筛选、搜索
- 骨架屏、错误重试、卡片展开（key_points、content_type）
- 信源名称展示（`source_name`）
- Favicon + 动态标题

**体验缺口（商业产品视角）**：

| 问题 | 影响 | 优先级 |
|------|------|--------|
| 健康 Tab 显示 `source_id` 而非名称 | 运维可读性差 | P1 |
| `CATEGORY_COLORS` 前端硬编码 | 新分类无颜色映射 | P2 |
| 统计栏无「最近采集时间 / 失败信源数」 | 用户不知道数据是否新鲜 | P1 |
| 无趋势图 / 历史对比 | 无法回答「这周政策类是否增多」 | P2 |
| 深度阅读依赖 `content` 字段，多为摘要 | 深度视图价值不足 | P2 |
| 无领域切换 UI（仅 URL `?domain=`） | 双领域用户操作繁琐 | P2 |
| Tailwind CDN + Google Fonts 外链 | 内网部署可能失败 | P3 |

### 4.2 API 面（`engine/output/api.py`）

**端点覆盖完整**：items、dates、stats、categories、sources、evolution、health、trending、report、RSS、Skill。

**缺口**：无 `/api/trends`；stats 字段偏少；china-africa 无独立 Scheduler。

## 六、产品目标规划（商业迭代视角）

### 北极星指标（North Star）

> **每周活跃使用天数 ≥ 5**，且用户从打开 Dashboard 到找到 3 条可用情报 **< 10 分钟**。

### 分层目标

| 层级 | 目标 | 时间 |
|------|------|------|
| **L1 可信** | 数据新鲜、失败可见、推送准时 | 当前 → 2 周 |
| **L2 好用** | 双领域对等、内容够深、趋势可感 | 2–6 周 |
| **L3 增值** | 导出/订阅/Agent 工作流 | 6–12 周 |
| **L4 产品化** | 多实例部署手册、成本仪表盘 | 按需 |

## 七、后续开发与优化任务（按商业优先级）

### Phase A：运营可信（1–2 周）— 「让用户相信系统」

> 商业逻辑：情报产品最先死在没有信任，不是缺功能。

#### A1. 数据新鲜度可视化 【P0 · 1 天】

- **任务**：`/api/stats` 增加 `last_fetch_time`、`last_fetch_errors`、`last_pipe_duration`
- **Dashboard**：统计栏显示「最近采集：2h 前 · 3 个信源失败」+ 红/黄/绿指示
- **验收**：用户 3 秒内判断「今天的数据是否可信」

#### A2. 健康 Tab 可读性修复 【P0 · 0.5 天】

- 信源列表显示 `source_name`，`source_id` 作副文本
- 侧边栏信源健康状态着色（API 已有 `health` 字段，前端未用）

#### A3. china-africa 领域补齐 【P0 · 2 天】

| 子任务 | 说明 |
|--------|------|
| 新建 `keywords.yaml` | 从 categories 关键词 + scoring 语义抽取初始集 |
| `categories.yaml` 加 `freshness_days` | policy 30d、risk 3d、其余 7–14d |
| Scheduler 增加 china-africa 任务 | 如 9:00 采集+推送 |
| 跑一轮完整 `pipe` 并人工验收精选质量 | 调 scoring.md |

#### A4. 运营 SOP 文档 【P1 · 0.5 天】

- 每日：看 Dashboard 日报 + 飞书推送
- 每周：`evolve all` + 健康 Tab 处理低效信源
- 每月：审 scoring.md 校准建议、审关键词 staging 结果
- 不写新代码，但**决定产品能否持续运转**

---

### Phase B：内容深度（2–3 周）— 「让精选值得读」

> 商业逻辑：用户留存取决于「点开链接前就已经获得足够信息」。

#### B1. 全文/正文增强 【P1 · 3 天】

- RSS 缺 content 时自动抓取原文（readability / BS4）
- `RawItem.extra` 或新字段存 `full_content`
- 深度阅读 Tab 展示全文摘要（≥ 500 字）
- **指标**：深度阅读 Tab 点击率提升（可埋点或人工观察）

#### B2. 评分质量闭环 【P1 · 2 天】

- CLI `filter` 结束展示「解析失败 N 条 / 重试成功 M 条」
- 每周自动跑 `evolve scoring`，将建议写入 `data/reports/` 并飞书摘要
- 人工每月审一次 scoring.md（半自动，不全自动改 prompt）

#### B3. 日报产品化 【P2 · 1 天】

- 日报 Markdown 增加「本周趋势一句话」（对比上周精选数）
- JSON 日报字段与 Dashboard 对齐（key_points、entities）
- 支持 `report --date YYYY-MM-DD` 补生成历史日报

---

### Phase C：洞察增值（3–4 周）— 「从日报到决策支持」

> 商业逻辑：从「今天有什么」升级到「这周发生了什么变化」。

#### C1. 趋势统计 【P2 · 3 天】

- `daily_stats` 表：每日采集/精选/分类分布快照
- `/api/trends?days=30` 端点
- Dashboard 新 Tab「趋势」：精选率折线、分类堆叠（Chart.js 或纯 CSS）

#### C2. LLM 成本仪表盘 【P2 · 2 天】

- `llm_usage` 表持久化每次调用
- `/api/stats` 返回本月 token / 估算费用
- Dashboard 健康 Tab 或统计栏展示「本月 LLM 花费 ¥X」
- **商业意义**：内部产品也要算 ROI

#### C3. 领域切换与多领域首页 【P2 · 1 天】

- Header 领域下拉：elderly-care / china-africa
- 可选：首页卡片展示两领域「今日精选数」一览

---

### Phase E：增长扩展（6 周+，按需）

仅在 Phase A–C 稳定、elderly-care 周活达标后启动：

| 方向 | 说明 | 前提 |
|------|------|------|
| 导出 | 精选列表 → Markdown/飞书文档 | 内容运营有明确需求 |
| Agent 工作流 | Skill + `/api/trending` 驱动自动选题 | 内容 pipeline 已接入 |

| 用户反馈 | 条目「有用/无用」→ 反哺评分 | 有稳定用户群 |
| 认证/权限 | 仅在外网暴露时考虑 | 明确安全需求 |

## 十、总结

**当前状态**：Intel Pipeline 已完成从「技术 Demo」到「内部可用情报系统」的主体建设——流水线、统一 Dashboard、进化闭环、推送、测试框架均已落地。`PRODUCT_PLAN` Sprint 1–5 基本完成。

**核心缺口**不在「缺一个大功能」，而在三块商业短板：

1. **运营可信**：数据新鲜度、失败可见、双领域对等（china-africa）
2. **内容深度**：深度阅读价值不足，全文未提取
3. **趋势洞察**：只有日报快照，没有「变化」叙事

**建议下一步**：优先执行 **Phase A（运营可信）**，尤其是 A1 数据新鲜度 + A3 china-africa 补齐——这两项投入小、对「每天用」的体验影响最大。

如果你希望，我可以从 **A1（stats API 增强 + Dashboard 统计栏）** 或 **A3（china-africa keywords + freshness_days + scheduler）** 直接开始实现。
